# 实时语音交互与断线恢复需求及详细设计

## 1. 文档信息

- **需求名称**：患者端实时语音交互与医护端语音监控
- **适用范围**：入院量表评估 AI 对话模式
- **设计日期**：2026-08-19
- **修订日期**：2026-08-20
- **目标版本**：语音交互一期
- **相关文档**：
  - `docs/需求1-入院量表评估.md`
  - `docs/后端详细设计方案.md`
  - `docs/API接口文档-第一期文本闭环.md`

## 2. 需求背景

当前系统已经完成“患者端文本输入 → Dialog Agent → Redis Stream → SSE → 患者端/医护端”的文本闭环。Redis Stream 的核心作用不是替代模型，而是将业务事件从实时连接中解耦出来，使患者端或医护端发生网络中断时，后台任务仍可继续执行，客户端恢复连接后可以使用 `Last-Event-ID` 从上次游标之后继续消费事件。

现需在不改变现有纯文本对话行为的前提下，新增患者端实时语音交互模式：

1. 患者可在原有 AI 对话页面切换“语音对话”和“文字输入”模式。
2. 语音模式使用阿里云百炼 Qwen 实时语音模型，通过 WebSocket 接收患者 PCM 音频并输出模型音频。
3. 患者语音转写、AI 文本、工具调用、宣教/知情同意、Schedule 约束、Extraction 结果和任务状态继续进入现有 Redis Stream/SSE 业务事件链路。
4. 医护端监控页面同步接收患者语音和模型语音，并支持播放。
5. 患者端断网或 WebSocket 错误时，后台语音会话和业务任务尽可能继续运行；重连后通过 Redis Stream 恢复文本、转写、进度和已持久化音频事件。

## 3. 非目标

本期不做以下改动：

- 不修改现有文本 `POST /api/dialog/message` 的协议和行为。
- 不将文本 Dialog Runner 改造成长驻实时语音 Runner。
- 不把 PCM 音频块直接写入 Redis Stream。
- 不承诺上游模型 WebSocket 尚未返回的音频可以精确断点续传。
- 语音模式使用 Qwen Audio Realtime 官方 `server_vad` 自动检测患者语音起止；
  push-to-talk 仅作为协议兼容能力，不作为患者端默认交互方式。
- 不实现真正跨地域、跨进程的实时模型连接迁移；后台连接由单个 Voice Gateway 进程托管，进程异常时按会话快照重建。

## 4. 现有系统架构事实

### 4.1 文本链路

```text
患者 POST /api/dialog/message
  -> PostgreSQL 保存患者消息
  -> DialogEventPublisher 发布 patient_answer
  -> Celery 独立派发 Dialog / Schedule / Extraction
  -> Dialog Agent 生成 AI 文本
  -> dialog_stream:{session_id}
  -> SSE 患者端与医护端
```

文本链路的可靠性来源于：

- PostgreSQL 保存完整对话历史；
- Redis 保存 Agent 状态、Schedule 指引和输出快照；
- Redis Stream 保存可续读的业务事件；
- SSE 使用 Redis Stream ID 断线续读。

### 4.2 当前语音基础设施

项目已经具备：

- `DialogEngine` 语音/文本抽象；
- `EventType.DIALOG_AUDIO` 音频事件；
- `InteractionMessage.audio_url/asr_text/tts_text` 字段；
- 前端 16kHz PCM16 麦克风采集；
- 前端 PCM 音频播放器；
- 前端 `VoiceSocketClient` 控制消息模型。

但当前生产代码仍存在以下缺口：

- `SendMessageRequest.input_mode` 仅允许 `text`；
- Dialog Agent Runner 固定使用文本引擎；
- 后端尚无语音 WebSocket 路由；
- API 模式患者页未启用语音按钮；
- 前端实时事件处理暂时忽略 `assistant_audio_delta`；
- 医护监控页没有语音播放状态和语音事件适配。

## 5. 总体解决方案

采用“文本模式不动、语音模式独立接入”的并行架构：

```text
患者端文字模式
  -> 现有 REST + Celery + Redis Stream + SSE（保持不动）

患者端语音模式
  -> 患者 WebSocket
  -> 后端 Voice Gateway（会话拥有者）
  -> Qwen-Audio-Realtime / Qwen-Omni-Realtime WebSocket
  -> 音频通过患者 WebSocket 低延迟返回
  -> 转写/文本/工具/进度通过 Redis Stream + SSE
  -> Schedule Agent / Extraction Agent 继续独立运行
```

后端 Voice Gateway 必须托管上游模型 WebSocket，不能让浏览器直连百炼。原因：

1. 浏览器断线时，后端仍可继续消费模型输出；
2. 业务事件可以持续写入 Redis Stream；
3. 患者重连后可重新绑定同一个后台语音会话；
4. API Key、业务提示词和工具协议不会暴露给浏览器。

## 6. 语音交互协议

### 6.1 客户端到后端

WebSocket 路径：

```text
/api/ws/dialog/{session_no}/voice
```

后端连接百炼 Realtime 上游时，会自动将配置中的 `model` 补入上游 WebSocket
URL 的 `model` 查询参数；浏览器端不接触百炼 URL 或 API Key。

控制消息：

```json
{"type":"start","task_id":"1","session_id":"S-001","format":"pcm_s16le","sample_rate":16000,"channels":1}
{"type":"interrupt"}
{"type":"pause"}
{"type":"resume"}
{"type":"close"}
```

`commit` 只保留给非 `server_vad` 的手动模式；患者端默认的连续语音模式不发送该事件。

二进制消息：

- `start` 后发送 16kHz、16bit、单声道 PCM little-endian 音频帧；
- 服务端仅在当前会话属于患者且任务处于可交互状态时接受音频；
- `server_vad` 下浏览器持续发送音频，由上游 `speech_started` / `speech_stopped`
  自动划分轮次；AI 播报期间仍保持采集，以便患者自然说话打断。

### 6.2 后端到客户端

控制消息：

```json
{"type":"ready"}
{"type":"state","state":"listening"}
{"type":"state","state":"transcribing"}
{"type":"state","state":"thinking"}
{"type":"state","state":"speaking"}
{"type":"error","code":"VOICE_SESSION_ERROR","message":"语音会话暂时不可用"}
{"type":"closed"}
```

音频消息：

```json
{
  "type":"audio",
  "sequence":12,
  "sample_rate":24000,
  "audio_base64":"..."
}
```

音频只通过 WebSocket 实时发送。Redis Stream 不存放每个音频块，只存放音频完成或音频分片索引事件。

## 7. 语音轮次与 Agent 协作

语音模式使用官方 `server_vad` 时序：

```text
患者端持续发送 input_audio_buffer.append
  -> Qwen 发布 input_audio_buffer.speech_started
  -> 患者打断 AI 时立即清空客户端播放缓冲并取消当前响应
  -> Qwen 发布 input_audio_buffer.speech_stopped
  -> Qwen 自动提交当前语音轮次并自动触发模型响应
  -> Qwen 发布患者最终转写
  -> 保存患者语音消息（content_text/asr_text）
  -> 发布 user_transcript_completed
  -> 发布/执行关键词约束
  -> 派发 Schedule Agent 和 Extraction Agent
  -> 接收 AI 文本、音频和工具调用
  -> 保存 AI 完整消息
  -> 发布 assistant_message_completed
  -> response.done 后完成本轮状态
```

`server_vad` 模式下，客户端不发送 `input_audio_buffer.commit`，也不为普通语音
轮次发送 `response.create`。服务端根据 `threshold` 和
`silence_duration_ms` 自动判断轮次边界并触发回复。

### 7.1 Schedule Agent

Schedule Agent 不阻塞 Qwen 已自动开始的当前响应。收到
`input_audio_buffer.speech_started` 后，Voice Gateway 在当前患者发言结束前读取
Redis 中上一轮已经生成的最新 Schedule 指引，并通过 `session.update.instructions`
注入当前会话；患者最终转写完成后再异步派发 Schedule Agent，为下一轮生成新指引。

当前患者转写产生的关键词约束若晚于本轮自动响应启动，则默认作用于后续回复。
如果患者在 AI 播报时重新说话，按官方打断流程发送 `response.cancel`，客户端立即
清空尚未播放的 AI 音频，后续残余 `response.audio.delta` 不再播放。

### 7.2 Extraction Agent

Extraction Agent 只消费“患者最终转写 + AI 最终文本”形成的完整轮次，不消费音频增量。其结果继续发布：

- `extraction_updated`
- `progress_updated`
- `task_status_updated`

这样语音模式和文字模式共用结构化答案唯一事实来源，不以语音播放状态判断评估完成。

当 Extraction 确认全部必填、非派生结构化答案已经完整时，语音链路直接调用统一
评估完成服务，将会话置为 `completed`、任务置为 `pending_review` 并发布
`task_status_updated`。该收尾不派发文本 Dialog Agent，避免患者在纯语音页面收到一条
额外的文本结束语；当前最后一轮 Qwen 原生语音回复作为患者可见的收尾播报。

### 7.3 Function Calling

Voice Gateway 在首次 `session.update` 中注册现有 Dialog 工具定义，包含：

- `get_education_material`
- `trigger_consent_form`
- `request_nurse_assistance`
- 现有兼容工具

严格采用 Qwen Audio Realtime 官方事件顺序：

```text
response.created
  -> response.output_item.added（item.type=function_call）
  -> response.function_call_arguments.delta
  -> response.function_call_arguments.done
  -> 执行本地工具
  -> conversation.item.create（item.type=function_call_output）
  -> response.create
  -> 模型依据真实工具结果继续生成文本和语音
```

工具结果必须先由后端持久化并发布对应业务事件，再写回模型。宣教调用发布
`education_triggered`，知情同意调用发布 `consent_triggered`，呼叫医护调用发布
`handoff_requested`；Function Call 参数和工具结果同时保留审计记录。

## 8. 断线恢复设计

### 8.1 患者端断线、后端到 Qwen 仍在线

```text
患者 WebSocket 断开
  -> Voice Gateway 保留上游会话
  -> 继续消费上游事件
  -> 业务事件持续写入 Redis Stream
  -> 音频分片落本地/对象存储
患者重连
  -> SSE 使用 Last-Event-ID 恢复业务事件
  -> WebSocket 重新绑定后台会话
  -> 按缺失音频索引补播已保存片段
```

### 8.2 上游 Qwen 连接断开

服务端保存：

- `generation_id`
- `turn_no`
- `patient_message_id`
- `assistant_message_id`
- `text_snapshot`
- `audio_segment_no`
- `generation_status`

上游断开后：

1. 先发布可重试的 `agent_error`；
2. 使用 PostgreSQL/Redis 历史重建会话上下文；
3. 重新建立 Qwen 会话；
4. 未完成响应不假装成功；
5. 如无法安全续生成，保留已生成文本并让患者切换文字输入或重试。

### 8.3 恢复边界

Redis Stream 可保证业务事件的续读，但不能凭空恢复上游尚未返回的音频。能够恢复的是：

- 患者最终转写；
- AI 文本增量和完整快照；
- 工具、宣教、知情同意、人工呼叫事件；
- Extraction/Schedule/任务进度；
- 已经持久化的音频片段。

## 9. 音频存储策略

实时播放音频通过 WebSocket Base64 音频帧传输；患者端在语音模式开启期间持续
发送 16kHz PCM16。Voice Gateway 以 `speech_started` / `speech_stopped` 划分患者
音频轮次，持久化音频统一封装为浏览器可直接播放的 WAV（PCM16）文件。

Redis Stream 只保存：

```json
{
  "event_type":"dialog_audio",
  "generation_id":"GEN-001",
  "message_id":"MSG-AI-001",
  "segment_no":3,
  "audio_url":"/api/dialog/S-001/audio/GEN-001/segment-000003.wav",
  "audio_format":"wav",
  "sample_rate":24000,
  "is_final":false
}
```

## 10. 安全与权限

- WebSocket 必须复用患者 Cookie 身份校验；
- 患者只能连接自己的 `session_no`；
- 医护端不直接连接患者语音 WebSocket；
- 医护监控通过 SSE 接收音频索引，再通过受保护的音频接口播放；
- API Key 只在后端配置；
- 音频文件按 session/generation 隔离；
- 会话暂停、完成或取消后停止接收新的患者音频。

## 11. 可观测性与降级

必须记录：

- 上游模型连接建立/断开；
- 患者端连接建立/断开/重连；
- 每轮首个转写时间；
- 首个 AI 文本时间；
- 首个音频包时间；
- `response.done` 时间；
- 音频分片数和保存失败数。

降级顺序：

```text
实时语音失败
  -> 保留 SSE 和文字显示
  -> 前端提示“语音暂不可用”
  -> 切换文字输入
```

## 12. 验收标准

1. 纯文本模式现有测试和行为不回归。
2. 患者可以在同一对话页面切换文字/语音模式。
3. 语音输入可被后端接收并转发给 Qwen 实时模型。
4. 患者端能实时播放模型音频。
5. 患者最终转写、AI 文本、工具调用和进度能通过 SSE 展示。
6. 医护监控端能看到患者转写和 AI 文本，并播放双方已持久化音频。
7. 患者 WebSocket 断开后，后台业务事件继续进入 Redis Stream。
8. 患者 SSE 重连后可按 `Last-Event-ID` 恢复事件。
9. Schedule Agent 和 Extraction Agent 继续独立派发，不被音频分片阻塞。
10. 上游模型不可用时，系统不伪造成功，保留文字降级入口。
11. `server_vad` 自动识别患者停顿并生成回复，患者无需手动提交每一轮录音。
12. 患者在 AI 播报期间说话时能够打断播报，旧响应残余音频不会继续播放。
13. 语音模型可以原生调用宣教、知情同意和呼叫医护工具，并依据真实工具结果继续语音回复。
