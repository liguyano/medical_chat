# 后端详细设计方案

为了完成[docs/需求1-入院量表评估.md)]的需求, 我准备使用 langchain 框架作为 Agent 技术底座, Middleware 作为拦截中间件, 可以自由组装 AgentLoop.

我准备设计以下几个智能体:

1. 量表评估调度智能体, 它作为后台任务路由, 接收医护端选择的量表, 生成批量的量表问题队列, 引导 `对话智能体` 完成这些量表问题, 一方面减轻对话模型的推理损耗, 另一方面是提高量表问题的覆盖率, 避免问题不全面.

2. 面向患者交互的对话智能体-, 具备以下几个特点:
    - 1.1 语音对话: 使用端到端实时语音全双工大模型作为底座, 本次采用豆包实时语音模型作为实验, API文档如(https://docs.volcengine.com/docs/6561/2549778?lang=zh).
    - 1.2 引导式多轮对话：AI需引导患者与系统进行多轮对话交流，并引导患者回答映射到各类量表字段的问题，避免固定问答模板;
    - 1.3 共情能力：AI语言风格自然、亲切，符合老年人日常交流习惯，识别患者的情绪变化（如疲劳、焦虑、回避等）, 并进行适当回应与引导;

3. 字段抽取智能体: 结构化字段抽取任务, 任务相对简单.

## AgentLoop 设计方案

根据上述描述, 我认为各个智能体需要分开进程, 避免阻塞任务进行.

1. 量表评估调度智能体(Schedule Agent) AgentLoop 流程
量表评估调度智能体作为后台任务的资源调度, 需要拆解任务, 将杂乱离散的字段需求, 整理成一个有先后顺序的量表问题列表, 随后发送给 Dialog-Agent
后台资源调度celery任务一直跑(等待任务开启), 细节如下所示:
```text
医护端选择指定患者, 发布对话评估任务, 等待后台 Loading .
-> celery接收确定信号
-> Schedule Agent实例化
    -> 加载 system_prompt.
    -> user_prompt 组装记忆、时间、历史上下文.
    -> 加载工具列表 + Middleware列表
    -> 加载患者基础信息, 加载评估量表所有字段配置.
    -> 实例化成功(进程绑定)
-> Schedule Agent 输出量表问题列表(Task-todo)
```

由于患者与AI对话过程是一直进行的, 因此, Schedule Agent还需要获取患者与AI的对话记录, 判断是否正常开展.
```text
celery接收到 Dialog-Agent 发布信号(传输对话记录)
-> 获取进程绑定的实例化 Schedule Agent
-> 患者与AI对话记录组装User Prompt
-> Schedule Agent 根据上下文输出结果(即是否加入新的引导提示)
-> 发送给 Dialog-Agent AgentLoop
```


2. Dialog-Agent AgentLoop 流程
对话分为后台资源调度+用户交互两个阶段, 后台资源调度celery任务一直跑(等待任务创建对话智能体进程), 细节如下所示:
```text
医护端发布对话评估任务(患者号+量表评估调度智能体输出) -> 生成对话进程号(用户隔离)
-> celery接收确定信号, 拿到患者基础信息和Schedule Agent生成的量表问题列表(Task-todo)
-> dialog-agent 预热(提前初始化, 避免等待), 细节如下: 
    -> 加载 system_prompt
    -> user_prompt 组装记忆、时间、历史对话.
    -> user_prompt 组装评估任务(量表问题列表Task-todo + 加载用户基本情况)
    -> 加载工具列表 + Middleware列表
    -> 预热成功
-> 预热成功, 生成对话进程号, 该实例化智能体绑定进程号
-> 进程号将推送到患者端通知
-> (提前开场)对话智能体输出面向患者的开场提问. 例如: 开场白;
```

用户侧首次请求交互流程:
```text
患者端点击评估任务(拿到进程号)
-> 后端判断患者与进程号存在.
-> 根据进程号读取实例化对话智能体.
-> 患者端页面显示对话智能体输出的开场白.
-> 用户输入回答(传入的语音), 发送后端路由.
-> 注入智能体上下文(user_prompt).
-> 结合上下文, 对话智能体模型推理(实时语音全双工大模型).
-> 流式输出给患者端和医护端实时监控.

注意: 患者端此时交互完成了, 但是后台还需要将这份回答传给字段抽取模型, 抽取出结构化字段.
-> Middleware中间件 after_agent() 拦截结果
-> 将本轮模型问题+患者回答发送给另外两个后台任务: 字段抽取后台任务与量表评估调度后台任务.
```

用户侧多轮对话交互
由需求1可知, 当患者回答问题时, 出现了特征词(例如: 抽烟、喝酒等), 则需要字典库拦截, 引导模型对患者开展相关的宣教、知情同意书的签署.
并且, 量表评估进程是否遵循设定也需要把控, 所以多轮对话场景需要 Schedule Agent 的指令介入.

因此, 在多轮对话场景下, 交互流程如下所示:
```text
-> 患者多轮对话请求(文字或者语音)
-> 患者请求正则匹配字典库
-> 情况1: 匹配成功, 拦截请求, 强制注入新的约束提示词
    -> 抓取特征对应补充提示词, 注入模型上下文(User Prompt). 例如: `你必须询问患者抽烟多长时间`
-> 情况2: 未能匹配, 放行拦截.
-> 判断 Schedule Agent 是否发布新任务 
    -> 如果发布指令, 同样需要强制注入智能体上下文
-> 结合上下文, 对话智能体模型推理(实时语音全双工大模型).
-> 流式输出给患者端和医护端实时监控.

注意: 同理推送对话记录给后台.
-> Middleware中间件 after_agent() 拦截结果
-> 将本轮模型问题+患者回答发送给另外两个后台任务: 字段抽取后台任务与量表评估调度后台任务.
```

3. 字段抽取模型
这个任务比较简单, 就是写好提示词, 让模型按照指定JSON格式, 将AI对话记录, 按照评估量表的所有字段, 抽取出指定结构化字段, 然后把字段完成进度同步到医护端和患者端, 让用户能把控评估进度.


## 工具设计方案

需求1中提到AI需要自动识别什么时候要对患者做宣教, 并且还是分级宣教. 然后, 在特殊情况, 还会自动发布知情同意书的签署组件, 让患者在页面上自动签字.
根据这部分动态的需求, 我认为做成工具调用(Function_call)的方式, 能够更符合模型的自动感知.

- 分级宣教支撑工具: 各类宣教材料做成字典匹配的工具服务, 模型感知意图后, 调用工具, 根据参数的不同, 获取宣教材料的原始文本, 实时语音双工大模型可以自己播报文本给患者.

- 语音播报工具: 需求中提到, 需要自动播报宣教文档, 假设模型不支持语音, 那么就让模型调用该工具, 把文本交给工具, 让工具自动播报给用户.

- 知情同意书签署工具: 同理写成工具, 并且前端做唯一性组件匹配, 当模型调用该工具后, 获取文档资料, 然后前端组件同步显示知情同意书的内容, 以及页面上出现签字按钮(这部分就是前后端的任务了, 只要保存签字内容就好)
