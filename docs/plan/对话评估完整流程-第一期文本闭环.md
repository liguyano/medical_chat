# 对话评估完整流程（第一期·文本闭环）开发方案

> 目标：医护端选患者 → 勾真实量表 → 发布任务 → 三 Agent 后台协作 → 患者多轮**文本**对话 →
> 字段抽取 → 医护端实时监控，前后端完整跑通、可真人体验。
> 语音全双工为**第二期**单独立项（浏览器↔FastAPI WebSocket 直连），本方案不含。

- [X] 放弃字面「进程绑定」，改用**会话状态绑定 Redis**（session_no→state，dump/restore），跨 Celery 进程可靠。

## 1. 现状与差距（调研结论）

### 1.1 前端（已高度完成，主要是对接）
- 页面齐全：`nurse/patients`、`nurse/tasks/create`、`nurse/monitor/[taskId]`、`patient/dialogue/[taskId]` 等。
- 数据层 mock/api 双仓库（`src/lib/repositories/{mock,api}Repository.ts`），`NEXT_PUBLIC_DATA_MODE` 切换，mock 模式当前可完整演示。
- 传输：对话用 **SSE**（`/api/sse/dialog/{sessionId}`），非 WebSocket。
- 结论：前端**几乎不需要新建页面**，重点是让 api 模式对齐后端。

### 1.3 后端核心缺口（本方案要补的重点）
1. **无 Dialog 消费者 worker**：无人消费 `dialog_turn`→调 `handle_patient_input`→发 `dialog_message`。患者发消息后 SSE 收不到 AI 回复。**最大缺口。**
2. **schedule/extraction worker 从未被派发**：定义了但全项目无 `.delay()`。发任务时只派发了 preheat。
3. **待修坑**：`get_runtime_dependencies` 把 `tool_executor` 传成 `None`（触发工具会崩）；extraction runner 里 `assessment_instance_id=1` 等硬编码占位没接真实库；`build_dialog_agent` 是废弃 shim（违反无兼容层规则，删）。
4. **双 `dialog_turn` 发布隐患**：`send_message` 已发 answer="" 的 turn，中间件又发带 answer 的 turn，需理顺（见 4.3）。

### 1.4 数据缺口
- 5 个患者 + 住院记录（`patient`/`patient_encounter`/`care_task` 域）种子。
- 真实量表：5 个结构化 JSON（ADL/入院评估/Braden/跌倒/NRS2002）**转换**入 `assessment_scale`/`_version`/`_section`/`_question`/`_option` 5 表。
- 关键词规则：`interaction_rule` 表种子（抽烟/喝酒 → constraint_prompt）。

## 2. 目标架构（第一期文本闭环）

> **交互方向（关键）**：AI 扮演医护人员**主导问诊**。AI 先提问、患者后回答，AI 再依据答案 + 量表问题列表(Task-todo) + Schedule 约束提出**下一个问题/追问**。
> 所以「AI 输出」的语义是**下一个问诊问题**，不是「对患者输入的应答」；**开场白 = AI 提出的第一个问诊问题**，发生在患者任何输入之前。

```text
[医护端]
  选患者(GET /api/patients/in-hospital)
  勾量表(GET /api/scales)
  发任务(POST /api/tasks, collection_mode=ai_dialogue)
      │
      ▼ task_service.create_task
  一次派发四个后台任务(.delay):
    ├─ dialog_agent_preheat(已有)        ← 预热(装配 agent + 载入 Task-todo)
    ├─ dialog_agent_worker(核心缺口)     ← AI 主导问诊, 产出「下一个问题」
    ├─ schedule_agent_worker(接线)       ← 消费患者答案, 偏离/漏项→ConstraintEvent
    └─ extraction_agent_worker(接线)     ← 消费(AI问+患者答), 抽字段→ExtractionResultEvent

  AI 主导问诊循环 (dialog_agent_worker):
    ① 会话开始: 取 Task-todo 首题 → 发开场提问(dialog_message) 到 dialog_stream
    ② 阻塞等患者答案(patient_answer 事件)
    ③ 收到答案后: 从 DB 历史重建 TextChatEngine
       → 中间件 before(关键词命中/Schedule约束→注入追问指令)
       → 模型推理产出「下一个问诊问题/追问」
       → 中间件 after(把 [本轮AI问 + 患者答] 推给 extraction/schedule)
       → 发下一问(dialog_message) 到 dialog_stream → 回到 ②
    ④ Task-todo 问完且无约束追加 → 发 session_end
[患者端]
  建 SSE(GET /api/sse/dialog/{session_no})  ← 收 AI 提问/进度(开场白即首问)
  答问题(POST /api/dialog/message)          ← 落库(患者答)+发 patient_answer 事件
[医护端监控]
  建 SSE(GET /api/sse/monitor/{session_no}) ← 只读同一 stream(AI问+患者答)
```

### 2.1 会话状态绑定（替代进程绑定）
- 每个 session_no 的 Dialog Agent 状态存 Redis：`dialog_agent:state:{session_no}`（含 turn_counter、当前 Task-todo 指针、消费游标 last_event_id）。
- Dialog worker 每次循环从 `dialog_stream:{session_no}` 阻塞读**患者答案事件**；文本引擎的 `messages` 每轮从 **DB 历史**重建（TextChatEngine 无需持久化内存态），据此推理出**下一个要问的问题**。
- 好处：worker 崩溃/重启后可从游标 + Task-todo 指针续跑，任意 Celery 进程都能接管，无需「进程绑定」。

- 覆盖差异化画像：如「老年+跌倒风险」「营养不良」「吸烟史」等，方便体验关键词拦截与不同量表。

### 3.2 真实量表入库（5 表转换）
- 脚本：`backend/scripts/seed_scales.py`（新建），读 `docs/structured/assessment-scales/*.json`。
- 转换映射（JSON → 表）：
  - `assessment_scale`：scale_code=index.id（nrs2002/braden_pressure_injury/...），scale_name=title，form_type。
  - `assessment_scale_version`：v1.0，publish_status="已发布"，effective_time=now。
  - `assessment_section`：按 JSON 分组（initial_screening/scoring.components/patient_fields 等归组）。
  - `assessment_question`：逐字段/逐题，question_code、question_name、patient_text（面向患者问法）、question_type（单选/多选/数值/布尔）、required、sort_no、derived（计算题标 True 由加载器排除）。
  - `assessment_option`：选项含 clinical_score（用于评分）。
- **注意**：JSON 是领域结构，非题库结构，转换需人工规则；`patient_text`（口语问法）多数 JSON 没有，需生成（见风险 6.1）。

### 3.3 关键词规则种子
- 脚本并入 `seed_demo.py` 或独立 `seed_rules.py`：写 `interaction_rule`，如 keywords=["抽烟","吸烟"] → prompt="患者提到吸烟，你必须追问吸烟时长与每日支数，并触发戒烟宣教工具"。

### 4.3 核心：Dialog 消费者 worker（最大缺口）
> 语义：AI **主导问诊**。worker 不是「把患者输入变成 AI 回复」，而是「依据 Task-todo + 患者上一轮答案 + 约束，产出**下一个要问患者的问题**」。
- [ ] 4.3.1 新建 `app/workers/dialog_agent_runner.py`：`DialogAgentRunner`，仿 ScheduleRunner 结构，注入 loader(Task-todo)/history_manager/redis/publisher/model。
- [ ] 4.3.2 循环：
  - 会话首轮：取 Task-todo 首题 → `agent` 生成开场提问 → 发 `dialog_message`（AI 问）。
  - 后续轮：xread `dialog_stream:{session_no}` → 只处理 **`patient_answer`**（患者答案事件）→ 从 DB 历史重建 TextChatEngine → 中间件 before（关键词/Schedule 约束→注入追问指令）→ `agent.next_question(...)` 产出**下一个问诊问题** → 中间件 after（把 [本轮 AI 问 + 患者答] 推给 extraction/schedule）→ 发 `dialog_message`（AI 问）。游标 + Task-todo 指针存 Redis。
- [ ] 4.3.3 新建 celery task `dialog_agent_worker`，在 tasks.py 注册，用 `create_chat_model` + `create_dialog_agent(engine_type="text")`。
- [ ] 4.3.4 **理顺事件方向（消除双 turn 隐患）**：明确两类事件——
  - **患者答案**：`POST /api/dialog/message` 落库后发 `patient_answer`（含 answer 文本），供 dialog/schedule/extraction 三 worker 消费；
  - **AI 提问**：Dialog worker 产出的下一问走 `dialog_message`（患者/监控端 SSE 消费，schedule/extraction **不**当作触发信号）。
  - 移除现状 `send_message` 发 `answer=""` 的 `dialog_turn` 与 `EventPublishMiddleware` 重复发 `dialog_turn` 的二义性，统一到上面两类。
- [ ] 4.3.5 开场白：由 dialog worker 首轮产出（Task-todo 首题的口语问法），发 `dialog_message`；preheat 只负责装配 + 载入 Task-todo，不再兜底发开场白（避免与 worker 双发）。

## 6. 边界与风险

### 6.1 风险
- **量表 `patient_text`（口语问法）缺失**：结构化 JSON 多为书面字段名，转成「面向患者的提问」需生成/人工润色。建议：转换脚本对无 patient_text 的题用规则套模板，体验前抽查。
- **SSE 事件契约**：前端事件类型比后端丰富，第一期只对齐主线事件，次要事件（education/consent/handoff）不发。
- **抽取写库链路**：extraction runner 的 writer 依赖 submission/instance 表，接真实库可能暴露 batch-A 未覆盖的字段，需边接边补。

### 6.2 第一期明确不做
- 语音全双工（第二期）。
- pause/resume/handoff/rating/consent 签署/quality review/questionnaire 表单流（非体验主线，后续批次）。
- 测试脚本（交他人；本方案只产出必要的测试计划文档）。

## 7. 验收（体验路径）
1. 医护端登录 → 患者列表出现 5 个种子患者。
2. 选 1 患者 → 勾 2~3 个真实量表 → 发布 AI 对话任务 → 得到 task/session。
3. 患者端打开对话页 → 看到 AI 开场白。
4. 多轮问答；回答含「抽烟」时 AI 追问吸烟细节（关键词拦截生效）。
5. 医护端监控页实时看到同一对话流。
6. 抽取结果随对话增量出现（医护端/完成页可见结构化字段）。
7. 全程无需 mock，`NEXT_PUBLIC_DATA_MODE=api`。

## 8. 执行顺序建议
数据种子(3) → 后端接口+worker(4) → 前端对接(5) → 联调(7)。
其中 4.3 Dialog worker 是关键路径，优先做通「发消息→SSE 收到 AI 回复」最小闭环，再叠加 schedule/extraction。
