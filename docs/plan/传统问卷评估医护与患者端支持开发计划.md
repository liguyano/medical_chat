# 传统问卷评估医护与患者端支持开发计划

## 1. 需求分析与可行性结论

### 1.1 需求目标

当前评估任务发布的真实 API 模式只展示 AI 对话采集，医护端无法选择传统问卷。需要恢复并完成以下闭环：

1. 医护端发布任务时可以选择“传统问卷”或“AI 对话”。
2. 传统问卷任务创建后立即对患者可见，不经过 AI 首问准备流水线。
3. 患者端按本次任务实际绑定的已发布量表展示题目、分组、选项、单位和校验规则。
4. 患者答题支持草稿保存、刷新/退出后恢复、条件题处理和必填校验；所有当前可见必填题完成后才能提交。
5. 患者正式提交后，答案、选项快照、计分/风险结果和提交状态写入后端，任务进入待护士复核。
6. 医护端能够查看患者原始问卷提交，展示真实选项标签和计分结果；传统问卷不生成虚假的 AI/护士对比。
7. 护士复核、退回重填、最终确认继续复用现有评估复核与护理计划闭环。

### 1.2 现状证据

- 后端 `CreateTaskRequest.collection_mode` 已允许 `traditional_form`，`care_task.collection_mode` 及 `assessment_instance` 也已有对应字段。
- 后端传统任务创建逻辑已经存在：任务状态为 `pending`，准备状态为 `not_required`，并设置 `patient_visible_at`；不会创建 AI `interaction_session`。
- 前端创建页虽然定义了两个采集方式，但在 API 模式使用 `.filter((item) => !apiMode || item.value === 'ai_dialogue')` 隐藏了传统问卷，并明确提示“传统问卷将在后续接口开放后启用”。
- 前端已有传统问卷页面、任务路由、Zustand 草稿状态，以及 `saveQuestionnaireDraft` / `submitQuestionnaire` Repository 方法，但 API 模式页面仍使用 `prototypeQuestions` 和本地草稿。
- 后端当前没有 `/api/tasks/{task_ref}/questionnaire/draft`、`/api/tasks/{task_ref}/questionnaire` 或 `/api/tasks/{task_ref}/questionnaire/submit` 路由；现有前端调用会得到 404。
- 后端评估执行表已经支持 `patient_self` 等多方提交、答案选项快照、分数和护士复核，不需要另建一套“问卷表”。
- 当前任务 DTO 的答案进度主要按 AI `interaction_session` 统计，传统任务没有会话，必须改为按传统问卷提交统计。
- 当前护士复核页面主要读取 `useTaskStore` 中的本地提交答案和原型题库，API 模式无法可靠回放真实传统问卷提交。

### 1.3 可行性结论

**可以完成，建议按后端真实问卷闭环实施，而不是只放开前端按钮。**

现有领域模型已覆盖任务、量表版本快照、评估实例、患者提交、答案/选项、计分和护士复核，主要缺口集中在 API、授权、答案转换和前端数据源。预计无需新增业务表；草稿可使用 `assessment_submission.submission_status=in_progress`，正式提交改为 `submitted`。如实现阶段发现需要数据库级幂等约束，再补充 Alembic 迁移，不预设重复建设表结构。

## 2. 范围与边界

### 2.1 本次包含

- 医护端真实 API 创建任务时的两种采集方式。
- 患者端传统问卷题目读取、草稿保存、恢复和正式提交。
- 必填、题型、选项、数值/日期校验和当前任务量表范围校验。
- 传统问卷答案的结构化持久化、选项审计快照、规则计分和风险结果。
- 传统问卷任务进度、任务状态、患者可见性和复核回放。
- 医护端传统问卷结果查看、复核/退回/确认。
- Mock 模式现有演示流程的兼容。
- 后端/前端单元测试、接口/集成测试、浏览器验收和文档同步。

### 2.2 本次不扩展

- 不改变 AI 对话、语音、SSE、Schedule/Dialog/Extraction Agent 主流程。
- 不把传统问卷改造成 AI 与护士的人机对比；传统问卷仅保留患者提交、护士独立提交和最终确认。
- 不新增量表审批工作流；只消费当前已发布且生效的量表版本。
- 不允许患者端自行修改任务绑定量表、评分规则或必填约束。
- 不把前端 Mock 题库作为 API 模式兜底数据源。

## 4. 预期接口草案

> 最终字段以 3.1.3 契约冻结为准，以下用于评估实现范围。

| 方法 | 路径 | 身份 | 作用 |
| --- | --- | --- | --- |
| `GET` | `/api/tasks/{task_ref}/questionnaire` | 患者或责任护士 | 查询任务绑定量表、题目、选项、当前草稿/提交和计分结果 |
| `PUT` | `/api/tasks/{task_ref}/questionnaire/draft` | 患者 | 保存传统问卷草稿，支持幂等更新 |
| `POST` | `/api/tasks/{task_ref}/questionnaire/submit` | 患者 | 校验必填并正式提交，进入待护士复核 |
| `POST` | `/api/tasks/{task_ref}/review` | 责任护士 | 复用现有接口保存护士独立/最终复核结果 |

## 5. 风险与处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 当前结构化量表仍有 `审核中` 版本 | 任务无法创建 | 继续遵守“只加载已发布且生效版本”的既有规则；测试环境显式导入已发布版本 |
| 数据库题目未持久化复杂条件逻辑 | 客户端可能错误判断可见题 | 必填/可见判断以后端为准；若临床规则需要复杂条件，先扩展量表配置快照和服务端规则评估 |
| 前端旧 sessionStorage 存有原型任务/答案 | 页面显示旧数据 | API 进入任务和复核页先清理并以服务端快照重建；本地草稿只作为待同步缓存 |
| 患者重复点击提交或网络重试 | 产生重复提交/重复护理计划 | 任务实例行锁 + 当前患者提交复用 + 状态幂等；护理计划派发使用现有幂等机制 |
| 传统问卷没有交互会话 | 复用 AI 进度代码会统计为 0 | 传统路径独立按 `patient_self` 提交统计，AI 路径保持会话统计 |
