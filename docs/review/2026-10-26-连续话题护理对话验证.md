# 连续话题护理对话验证

## 根因和修改
上一版只保证兴趣引入和一次细节展开，文字后续仍由题序选择目标；语音上游重连复用了初始指令，且没有恢复历史交流，可能重复自我介绍。

文字新增 SDK 内部话题轮次规划器，使用有效结构化答案的权威缺项与最近历史选相关目标和衔接方式；允许从散步、坐下歇息衔接起身，而不是机械进入列表中的进食题。规划不能写临床答案、计分或宣布完成，越界目标与解析错误进入原有失败事件和重试。

共享规则禁止让患者选择量表分类、重复开场和无依据夸赞。纯通话确认不进入评估问句；同时表达不适时不吞掉后半句。

语音新连接从已落库消息恢复最近交流，客户端在内存滚动保留最近 16 条交流，断线重连使用最新约束和交流上下文。评分、数据抽取和完成工具保持原边界，不访问或重新创建已清空的患者任务。

## 验证
- 新规划器缺失、重连缺失历史记忆的测试先失败，再实现。
- 全部 350 项后端单元测试通过；全部改动 Python 文件 Ruff 检查通过。
- 使用用户此前明确授权的相同阿里云 qwen3.8-max 目的地，仅传内部提示词和虚构对话，执行文字与语音提示文本模拟各六轮，共 2 项测试通过。
- 文字第 1 轮选择起身缺项而非列表中更靠前的进食；两组均从散步/坐下休息自然进入起身，再聊做饭、吃饭与睡眠。第 2 轮插入“听得到我说话吗”，回复仅作通话确认，没有重复开场。
- 连续检查未出现“评估表”“选项”“来分类”“可以开始吗”等问卷/开场话术。已明确的行走与起身事实未在后续轮次重新问。

## 边界
两组合成对话不是每次输出质量的保证；语音组没有连接真实麦克风、ASR/TTS 或真实 WebSocket。脚本中由测试提供假定已完成题集，未验证真实 Extraction 入库准确率；真实数据库故障与 Worker 重启恢复需要另做集成验证。
文字每轮新增一次轻量规划模型调用，会增加响应延迟；语音仍由实时模型直接推进，无新增逐轮文本规划调用。
本次未启动前后端服务，不改 main 和备份、不推送；用户原有未提交文件保持原样。

独立只读审查已核对题号边界、失败重试、缺项选择、历史去重与语音重连，无阻塞发现。
